# MarketFlow Backend Reality Audit

**Audit date:** 2026-11-24  
**Scope:** Existing application source, registered Laravel API, current PostgreSQL catalog and selected non-sensitive row counts, frontend wiring, and automated tests.  
**Disposition:** Findings only. No application feature or source code was changed for this audit. No real PostgreSQL rows were inserted, updated, or deleted; no migrations or seeders were run; `.env`, tokens, and Meta OAuth connection records were not accessed.

## Executive summary

The repository contains a substantial, authenticated Laravel API and a matching React application for the listed modules. The current PostgreSQL catalog has **46 base tables, 488 columns, 92 foreign-key constraints, and 141 indexes**. The migration ledger has 28 applied entries matching the repository's 28 migration files. Catalog inspection was read-only and rolled back.

The full Laravel suite passed: **171 tests, 1,254 assertions**. The test configuration uses **SQLite `:memory:`**, not PostgreSQL. A frontend production build had passed in the immediately preceding route-verification work. Neither result is evidence of a real, browser-driven workflow against PostgreSQL. The browser page available to the audit was inaccessible, so **no UI → API → PostgreSQL → UI workflow was browser-verified**.

The largest functional gaps are integration and attribution gaps, not absence of all CRUD:

* Campaigns store manual campaign metrics and link to Projects; they do not have Meta ad-account/campaign identity or synced insights. CRM leads can reference campaigns, but Sales orders and Finance transactions do not. Campaign revenue/profitability therefore is not proven end-to-end attribution.
* Sales and Delivery each have their own shipment records. `delivery_shipments.sales_order_id` is not a foreign key, and the Delivery controller/service does not call the Sales order lifecycle when delivery updates arrive. No production Delivery provider adapter was found; the registry is only populated by a fake in tests.
* Analytics and Reports aggregate application records, not a persisted Meta insights history. The Meta API request is campaign-level, not the latest ad-level creative/ad, and was not exercised against a real connected account.
* Workspaces, Projects, Campaigns, Strategies, Research, Audiences, Tasks, Calendar, CRM, Sales, Finance, Analytics, Reports, Archive, Meta Ads, and Delivery all have varying degrees of frontend/API/database implementation. See the module matrix for explicit limitations and source evidence.
* The repository has no approved design reference available beyond a hero image. Consequently, historical UI parity and which approved sections disappeared cannot be reliably established from the current checkout.

No completion percentage is given: there is no agreed denominator/checklist that makes a percentage meaningful.

## Evidence and status definitions

* **Verified** means a bounded behavior is supported by source and/or automated test evidence; it does **not** mean a full production workflow was browser-verified.
* **Partial** means some requested behavior exists but material parts of the feature, integration, validation, or end-to-end path are absent or unproven.
* **Missing** means no corresponding implementation was found in the inspected application.
* **Broken** means code/schema wiring has a concrete gap that prevents the claimed behavior or leaves it unsafe.
* **Not Tested** means the audit deliberately did not exercise it, or could not do so (for example, live Meta OAuth, an external delivery provider, or browser workflow).

### Audit execution

* PostgreSQL inspection queried catalog metadata and selected aggregate counts under read-only transactions, then rolled them back. No sensitive user, token, credential, or OAuth row values were read. Meta connection records were not queried.
* Selected counts found 1 workspace, 1 project, 1 calendar event, 1 CRM pipeline and 5 CRM stages. Campaign, audience, strategy, research, finance, Sales order/shipment and saved-report tables were empty in those selected counts. These counts deliberately excluded sensitive/authentication/integration records; a clean empty-data check does not demonstrate that future cross-tenant links are prevented.
* Selected cross-workspace mismatch checks found no existing mismatched rows in the sampled relationships.
* `php artisan test`: **171 passed, 1,254 assertions**. [backend/phpunit.xml](./backend/phpunit.xml) configures SQLite `:memory:`; this test run neither validates PostgreSQL-specific behavior nor touches the actual PostgreSQL dataset.
* Frontend `npm run build`: passed in the immediately preceding route verification. It verifies compilation, not UI behavior or backend connectivity.
* No browser workflow was verified. The available browser page identifier was unavailable. No original approved UI specification/screenshots were found.

The 28 migration files inspected are: `0001_01_01_000000_create_users_table`, `0001_01_01_000001_create_cache_table`, `0001_01_01_000002_create_jobs_table`, `2026_10_15_000001_add_profile_fields_to_users_table`, `2026_10_15_000002_create_workspaces_table`, `2026_10_15_000003_create_workspace_users_table`, `2026_10_15_000004_create_workspace_invitations_table`, `2026_10_15_000005_create_workspace_settings_table`, `2026_10_15_000006_create_workspace_audit_logs_table`, `2026_10_16_000001_create_projects_table`, `2026_10_16_000002_create_campaigns_table`, `2026_10_16_000003_create_tasks_table`, `2026_10_17_000001_create_finance_budgets_table`, `2026_10_17_000002_create_finance_transactions_table`, `2026_10_17_000003_create_calendar_events_table`, `2026_10_17_100001_create_audiences_table`, `2026_10_17_100001_create_crm_tables`, `2026_10_17_100002_create_marketing_strategies_table`, `2026_10_17_100003_create_market_research_projects_table`, `2026_10_17_210001_create_saved_reports_table`, `2026_10_17_230001_create_archive_entries_table`, `2026_10_17_230002_create_meta_ad_connections_table`, `2026_10_18_000001_create_delivery_integrations_tables`, `2026_10_18_000001_create_sales_tables`, `2026_10_18_140000_create_meta_oauth_transactions_table`, `2026_10_18_160000_create_password_recovery_codes_table`, `2026_10_18_170000_create_workspace_notifications_table`, and `2026_10_18_230000_add_preferred_account_to_meta_ad_connections`.

## B. Missing functionality and architectural defects

1. **Delivery → Sales synchronization is absent.** Separate shipment tables, no Delivery-to-order FK, no same-workspace existence validation for the supplied sales order, and no `OrderLifecycle` call from Delivery updates/webhooks.
2. **No real carrier adapter is registered.** The extension contract exists, but only test fakes were found. Dispatch/test/refresh cannot be considered production carrier integration.
3. **Campaign attribution is incomplete.** CRM leads may refer to campaigns; there is no implemented order-to-lead/campaign attribution path, no campaign FK on Sales/Finance, and no verified attribution policy.
4. **Meta reporting is not an analytics pipeline.** The current API fetches campaign-level live insights for the Meta view. No dated persisted insight snapshots feed Analytics or Reports; no ad-level latest-ad request was found.
5. **Report configuration is not fully honored.** The report service supports a limited set of aggregations; persisted `configuration` is not generally applied. There is no durable report-run/result history.
6. **Workspace member UI exceeds API surface.** Workspace CRUD exists, but the frontend service/routes do not provide member or invitation management operations for the displayed member-oriented sections.
7. **CRM-to-Sales customer identity is split.** `crm_customers` and `sales_customers` are different entities; no automatic conversion/identity bridge was found. `crm_leads.converted_to_customer_id` lacks FK enforcement.
8. **Business constraints are mostly application-side.** Same-workspace relationship validity, status combinations, totals, dates, and domain rules are not universally enforced through composite FKs or database check constraints.
9. **Legacy mock/fixture data remains in the tree.** Finance profitability and Reports have legacy fixture modules. Current pages are API-backed, so fixture presence alone is not proof active views use mock data; it does create risk of regression or misleading reuse.
10. **Design parity cannot be established.** No approved design artifact is present to compare; a code-only audit cannot safely infer which prior UI sections were approved or removed.

## C. Critical data-integrity and security issues

* **High — carrier status can diverge from Sales order status.** The independent Delivery update path records carrier shipment state but does not update Sales lifecycle/order state. The UI can therefore show inconsistent order/shipping state.
* **High — weak Delivery order reference.** `sales_order_id` has no FK and creation validates UUID shape without confirming the order exists in the same workspace. Orphaned or cross-tenant references are structurally possible.
* **High — cross-workspace links are not structurally constrained.** Most FKs do not include workspace ID. Request/controller authorization must correctly validate every linked record; zero observed mismatches in sparse data is not a control.
* **Medium — CRM conversion reference is unenforced.** `crm_leads.converted_to_customer_id` has no FK, permitting stale or invalid links if controller logic fails or future code bypasses it.
* **Medium — Sales values need invariant validation.** Order items are JSON and the schema does not itself ensure `subtotal`, `total`, item sums, shipping, COD and collection/payment states reconcile. Application validation and transaction tests should enforce consistent totals.
* **Medium — Meta config-cache risk.** The Meta service reads `env()` from service code. Laravel's production configuration cache can make direct `.env` reads unreliable; expose these values through `config()` and test cached configuration.
* **Security controls observed:** authenticated/tenant middleware is registered for protected API routes; workspace scoping/authorization services and fail-closed workspace scopes exist; Meta/Delivery credential fields use encrypted casts; OAuth state is transaction-backed; recovery endpoints are throttled. This review did not inspect secret values or test a real OAuth flow. No PostgreSQL row-level security policy was established by the inspection; tenant isolation relies on Laravel controls.

## E. Backend requirements for restoring/maintaining approved UI

The original approved design was not available in this checkout; therefore this section identifies backend needs implied by current UI, not a claim about the historical approved design:

* Workspace member/invitation views require list/invite/accept/revoke/role APIs and membership-scoped data.
* Campaign dashboards that present live Meta metrics need platform IDs, dated source snapshots, sync/error status, account timezone/currency, and defined attribution semantics.
* Sales reporting needs a CRM identity bridge, explicit campaign attribution events, and a policy for refunds, COD remittance, returns, and payment collection; separate campaign/finance/order tables do not supply this relationship.
* Reports must either implement saved `configuration` (fields, grouping, filters, date bounds) or constrain the UI to the report types and filters actually supported.
* Delivery controls require real provider adapters and stable mapping from provider status to shipment and order lifecycle; unsupported adapters should be shown as unavailable rather than as connected/operational.
* Where charts/cards display financial totals, label whether the value is recorded campaign metadata, Finance ledger, Sales orders, or actual Meta-reported spend; do not imply these are reconciled.
* Use the approved screenshots/specifications and browser tests to compare page sections, interactive states, empty/loading/error states, responsive layout, and action results. This audit cannot infer missing approved sections from current source alone.

## F. Ten highest-priority fixes

Ranked by data integrity, operational correctness, and misleading reporting risk:

1. **Unify Delivery and Sales shipment/order linkage:** add enforced order relationship and same-workspace validation; map authenticated/idempotent carrier events through `OrderLifecycle` transactionally.
2. **Implement and register a real Delivery provider adapter** before presenting dispatch/refresh/test as operational; exercise provider errors, retries, signatures, and webhook replay.
3. **Define conversion attribution and customer identity:** bridge CRM leads/customers to Sales customers/orders; record campaign touchpoints and document attribution window/source.
4. **Persist provenance-aware Meta insight snapshots:** retain account/campaign/ad identifiers, dates, currency/timezone, source and sync state; integrate only actual returned values into Analytics/Reports.
5. **Enforce tenant-consistent relationships:** validate every linked record under active workspace and consider composite unique/FK constraints for critical `(workspace_id, id)` references.
6. **Repair CRM conversion integrity:** add a foreign key for converted customer (with explicit null/delete semantics) and make conversion atomic/idempotent.
7. **Make financial invariants explicit:** reconcile order items, totals, shipping, COD, payment collection, refunds, and finance transactions; reject inconsistent or duplicate transitions at the service/database boundary.
8. **Honor or remove saved report configuration:** align frontend options, validators, report service and CSV output; cover every advertised report/filter type.
9. **Finish Workspace membership workflows** or remove/disable nonfunctional member/invitation UI until APIs exist.
10. **Add PostgreSQL-backed and browser end-to-end validation** using isolated test resources: authenticated multi-workspace CRUD, role denial, Sales→Delivery→Sales status, Meta snapshot→report, and export verification.
